# 算法引擎：从有限信息到可履行的安排

[文档导航](README.md) · [数据协议](data-and-scenarios.md) · [实验与指标](experiments.md)

> 本文定义目标计算逻辑，不声称仓库已有可运行内核。具体权重、模型系数和默认资源量尚需实现及实验确定。

## 引擎边界

引擎接收当前城市状态、截至当前时点可见的信息、策略配置和资源约束，输出候选方案、解释、确认后的资源占用以及事件与账目更新。模拟环境负责产生迁居、需求、采纳和取消等事件，两者分离，防止未来信息泄漏。

建议运行入口的概念协议为：
`run(initial_snapshot, visible_events, strategy_config, environment_config, seeds)`。
输出包括运行元数据、逐期状态、决策解释、事件、账目及指标。此处是接口设计，不是现有 API。

## 一次决策的顺序

1. **读取可见信息**：当前需求、意向、库存、维护状态、服务容量和既有承诺。
2. **筛除不合条件方案**：品类与适配性、成色接受度、可用窗口、运输与整备依赖、服务覆盖。
3. **估计未来情景**：从意向、历史需求与公开的季节假设估计供需和退出残值，报告不确定性。
4. **比较可行方案**：成本、可靠性、可流转性与风险分项展示；用户可以表达偏好和拒绝推荐。
5. **确认前再检查**：重验物件、需求、服务容量、资金和风险额度，防止多个候选重复占用资源。
6. **原子化登记承诺**：锁定条款与资源；任何一项失败，整次确认不成立。
7. **推进实际事件**：使用、维护、运输、检测、回购、取消、重新匹配，同步更新状态和账目。
8. **计算可追溯指标**：每项结果带运行标识、观察窗口、事件来源及分母。

硬条件不参与软评分抵消。低价格不能补偿时间窗冲突，也不能突破“仅接受新品”的个人要求。

## 成本与排序

用户净使用支出定义为：

**已实际支付的购入、服务与维护等支出 − 已实际收到的退出款。**

推荐阶段使用预计费用和预计退出款计算“预计净使用支出”，必须与已实现结果分开。对期末仍在使用的物件，预计残值不能当成已经到账的收入。候选方案注明承诺主体、检测条件、费用、窗口和不确定性。

初版可采用透明的加权排序作为设计选项：

`score = w_cost × normalized_cost + w_delay × delay_risk + w_operator × operating_risk − w_reuse × reuse_potential`

所有分项先定义量纲、范围及缺失处理，权重非负，固定相同归一化规则再比较。此公式是建议实现方式，不是已验证的现行算法；“可流转性高”不能压过用户的硬偏好。排序要有确定性平分处理，并保留分项解释。

## 可调项及影响

| 类别 | 参数示例 | 影响 |
| --- | --- | --- |
| 个人输入 | 居住期限、预算、二手接受度 | 可行集合与预计成本 |
| 环境假设 | 需求强度、推荐采纳率、取消率、预测误差 | 模拟环境与未来不确定性 |
| 资源 | 逐期服务容量、可用现金、风险额度 | 能否确认及如何排程 |
| 策略 | 成本/延迟/风险/流转权重、预测窗口 | 可行方案的排序与新增安排 |

参数页必须给出单位、范围、默认值的依据和受影响的规则。默认值未校准时标注“模拟假设”。修改参数作用于新运行或后续新决策，不追溯修改既有合同条款。

## 状态、资金与异常

物件至少区分使用中、待检测、整备中、可用、已预约、运输中、退出循环。物件的拥有者与使用者分开存储，具体所有权规则由方案声明。

确认回购时要记录未来付款义务与准备安排，实际付款才进入现金流水。现金余额、库存估值、未到期承诺敞口分别显示，不能相加后宣称可用资金充足。

| 异常 | 必须保留的规则 |
| --- | --- |
| 接手者取消 | 已确认回购不因此消失；转为库存、重新匹配或其他安排 |
| 预测残值下降 | 新报价可以调整，旧承诺条款不能静默降低 |
| 服务容量下降 | 显示延迟、替代服务或无法新增承诺，记录原承诺结果 |
| 现金不足 | 拒绝新增承诺；既有义务若无法履行，明确记录缺口/违约，不能删账 |
| 意向变更 | 更新预测；不自动按违约处理 |
| 正式承诺未履约 | 记录责任主体、原因与对应安排，支持纠错 |

## 策略边界

- **B0**：自由购买与事后出售；外部购买/退出选项也需明确成本和可获得性。
- **B1**：提前登记与匹配，使用已披露意向协调。
- **B2**：在同样已知信息基础上加入未来供需估计，协调购买建议、报价与资源。

B2 可能因预测误差、采纳反馈或承诺风险而劣于 B1/B0。实现不应预置其胜出。

## 解释记录

每个推荐保留：需求输入、筛除原因、费用分项、预测依据与版本、不确定性、可用资源快照、最终条款、接受/拒绝事件。每次状态和账目变化关联触发事件。这样的记录才能回答“为什么这次推荐变了”，也能让可视化使用同一份事实。
