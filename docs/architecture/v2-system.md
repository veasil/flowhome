# Flowhome v2：产品入口与可组合模块

状态：设计规范，尚未替换v1运行代码。沿用 docs/versions/v2-plan.md 的研究与验收目标。

## 一套产品，五个入口

软件服务的内部运营者、外部服务商都是用户。按任务组织入口，不按“城市/物件/算法/价值观”等主题堆叠页面。产品入口不等于部署单元，也不等于功能模块。

|入口（拟定路由）|使用者|打开后先看到什么|要完成的行动|
|---|---|---|---|
|居住服务 `/live`|购买者、退出者、下一位接手者|我的居住计划、待决定方案、正在履行的订单|购前表达偏好与居住期限；比较自售/保障；接受或拒绝；使用、退出、接手、申诉|
|运营台 `/ops`|组织运营者、分配相应权限的成员代表|待确认承诺、待处理异常、可用资金与到期责任|确认可承担方案、处置库存、重排履约、核对账目、执行经授权的规则|
|服务商工作台 `/partners`|检测、搬运、维修等外部团队|待接受任务、已约窗口、待结算服务|申报容量、接受/拒绝任务、执行并提交证据、处理异常、对账|
|研究开发台 `/lab`|数据、算法、实验与软件研究开发者|数据版本、待运行实验、失败案例、版本差异|生成城市、检查可见信息、替换算法、运行对照、诊断并导出复现包|
|项目页 `/`|公众、合作方、活动评委、潜在用户|生活问题、具体服务、版本状态、证据与参与入口|理解项目并进入对应服务；查看方法和限制|

下一位使用者属于居住服务中的接手流程。物件护照、价格明细、申诉、城市地图都是嵌入式能力，不再各自成为独立门户。同一人可拥有多个角色；模拟切换角色不是生产级授权。

## 同一单的贯穿路径

购买前居住需求 → 可行方案与退出选项 → 居民选择 → 组织确认并留存资金 → 使用 → 发起退出 → 服务商接受任务、检测与取件 → 组织释放合格库存 → 下一位确认并签收 → 分账、对账和可申诉记录。

所有入口围绕同一 `caseId / assetId / commitmentId / taskId` 查看各自投影；金额由账本生成，不在页面各算一遍。研究台的模拟运行用 `runId` 命名空间隔离，不能写回实际服务订单。未来若接真实数据，需明确去标识与授权范围。

预估一年后的服务能力不同于服务商已接受的具体预约。确认退出承诺后，服务商拒单或改期意味着组织需要重排或履行既定补救责任，不意味着可以取消对居民的原承诺。

## 模块化：先在同一个应用内建立边界

|模块|拥有的事实/产物|读入|允许的输出|独立优化重点|
|---|---|---|---|---|
|M0 公共契约与标识|schema、事件类型、版本与单位约定|产品定义|协议/fixture，不存业务状态|兼容性、字段语义、角色可见性|
|M1 城市数据与情景|合成世界、外部事件、观察投影|场景参数、种子、事件|ObservedSnapshot、世界实际结果（仅评估读取）|持续流入、行为校准、信息缺失|
|M2 算法引擎|预测/候选/解释，不拥有合同|仅可见快照、规则快照|带有效期与依据的Proposal|预测、可行匹配、选品、滚动决策|
|M3 交易与承诺|订单/合同状态及签订时条款|选择命令、建议、资金与容量检查|确认/拒绝/补救事件|可兑现性、幂等、生命周期|
|M4 外部服务履约|服务能力、预约、任务证据与状态|任务请求、服务商响应|接受/拒绝/完成/失败事件|检测标准、排程、合作方适配|
|M5 账本与库存成本|现金、留存、应付、库存成本记录|合法业务事件|现金桥/留存桥/成本桥及角色账单|对账、收入口径、资金压力|
|M6 共益规则与治理|费率/资格/服务标准版本、申诉与例外记录|共同规则、授权变更、证据|不可变PolicySnapshot、治理决定|报酬、公平进入、补贴和争议处理|
|M7 实验与评估|运行清单、指标口径、配对对照与证据|版本锁定的模块、种子、输出事件|可复现RunArtifact|识别预测效果、失败分析、分组指标|

这些模块是代码与业务责任边界。v2初期共用一次部署和事务存储，不为并行开发拆成八个网络服务。界面组件可以并行设计，但页面拆开不等于底层模块已经解耦。

## 谁可以写什么

- 算法不能付款、签合同或修改规则；它返回建议。
- M3接收命令后通过M5检查资金留存、通过M4检查当前可兑现的资源，在同一事务边界提交承诺及相关记账；不能先确认再补失败的占用。
- M4维护预约/任务，不能直接扣用户款；结算依据经校验的事件进入M5。
- M6发布新规则版本，不追溯改写旧承诺。规则变更需列出受影响角色与同责任实验是否失去可比性。
- 研究台可以改变实验世界，不可以把隐藏未来写进算法快照。研究人员的调参能力不等于运营授权。

## 共益不是装饰模块

共益政策必须影响具体操作：谁可参与、费率怎么算、劳动如何付费、补贴从哪里来、错误如何纠正。运营台管理规则和责任队列；居民与服务商各有申诉、查阅与参与入口；成员代表按授权审议。处理人员有利益冲突时回避，不允许运营方单方面裁定自身争议。

公开项目页展示规则原则、版本和聚合结果，不暴露个人账单。收入、学历、职业声望不作为综合信用分。算法报告群体差异，不能自行决定伦理取舍或改写共同规则。

## 异步组装方式

先锁定M0最小接口和共同案例。M1、M2、M4、M5、M6可分别基于明确标注的fixture研究；各角色UI基于相同fixture设计。mock只能替代尚未接入的依赖，不能作为真实性能证据。

整合时统一时钟、版本、事件序列与账目；以一件净水设备的全流程检验，再加入取消、重复回执、资金不足与服务商失败。接口变化提交兼容性提案，通知受影响模块后更新fixture及适配器，不能在自己的模块里静默修改字段。

## 当前能力边界

本轮交付：架构、契约草案、agent任务包/评审协议、可执行的工作流结构校验工具。本轮不声称已实现模块运行时、自动agent调度器、生产权限或真实共同治理。v1线上版本保留，v2实施按独立任务推进。
